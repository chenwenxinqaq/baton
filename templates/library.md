# §0 记忆维护规则

### 任务开始时怎么读

先读当前库的 §0，再用 `memory_search` 按任务关键词找相关主题，用 `memory_read` 核对原文。优先看相关 L0 约束、L1 方法、L2 偏好与 L3 快照。使用快照前核实当前源码、环境或项目状态。历史授权只在原来的主体、对象、动作和期限内有效。当前用户的指令优先于历史记忆；采用导入的偏好前，先确认是当前用户的选择。

### 何时写入

以下任一情况值得记录。事实一经核实就写；最终回复前再检查一次，有遗漏时先保存，再回复。用户无需每次提醒。

- 排查才得到的根因、踩坑经验，或与预期相反且已验证的结果。
- 下次任务能复用、又难以从现有文档恢复的方法或事实，例如经过验证的构建步骤、访问条件。
- 用户明确表达的长期偏好、对以往做法的纠正，或明确设定的长期操作约束。
- 代码和提交历史难以解释的项目决策、取舍、进展或阻塞变化。
- 用户明确要求“记住”或“记一下”的内容。沿用用户给出的适用范围和期限。

跳过普通对话流水账、只对本次任务有效的临时指令，以及从代码、README 或提交记录即可恢复的细节。需要后续验证的假设可在 L3 标为“未验证”，附上验证方法。事故等根因定位后再写入 L4。

### 选择层级

| 层级与目录 | 写入依据 |
| --- | --- |
| L0 `constraints/` | 用户明确设定的长期红线和授权边界。写清适用对象、动作、期限及例外。 |
| L1 `methods/` | 已验证、可跨会话复用的方法。写明触发条件、步骤和验证结果。 |
| L2 `preferences/` | 当前用户明确表达的偏好或纠正。写明适用场景和以后应采用的做法。 |
| L3 `projects/` | 以确认日期为准的项目决策、快照与阻塞。写清证据、待验证项和复核条件。 |
| L4 `archive/` | 已查明根因的历史事故。写明发生日期、影响、根因和实际复验范围。过期快照若移入归档，要保留其历史快照身份。 |

### 怎样写成下一次能用的条目

1. **先查后写。** 搜索同主题，读原文，再决定新建或更新。已有条目沿用原文件名和 `name`，保留仍有效的证据；把本次进展合入正文。一篇只讲一个主题，一次普通对话无需拆成多篇。
2. **写结论和边界。** 通过 `memory_upsert` 提交层级、稳定的 `name`、标题、摘要和正文。索引一篇一行，摘要直接给出结论。正文交代适用条件、证据与失效条件。手工维护时同步更新对应分层的索引行，保留无关内容。`body` 只写正文，frontmatter 和一级标题由服务端生成。手工维护时，每篇 frontmatter 至少包含 `name`、`description`、`type`；从 `user`、`feedback`、`project`、`reference` 里选择合适类型。
3. **写绝对日期。** 用 YYYY-MM-DD 分别记录事实的验证日期和文档的修改日期。编辑措辞时保留原验证日期。
4. **修订过期结论。** 新证据推翻旧判断时，更新原文和索引，注明撤回原因。仍有历史价值的旧快照可用 `memory_archive` 归档。同一主题只保留一个当前状态。
5. **保护敏感信息。** 凭据放在用户的凭据管理器或本地权限为 0600 的私有文件中，条目只记录必要的位置说明。仅在用户明确要求时修改 `user-managed/`。

例如，用户说“这次用 CSV”，只在当前任务执行；用户纠正“以后每周报告都要用 CSV”，更新对应的 L2 偏好。同样，任务失败但原因未明时，可在项目原篇记录阻塞及验证计划；找到根因后再归档事故。以上均为示例。
